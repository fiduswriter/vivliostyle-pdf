Client-Side Paged Media

J. Wilma and A. Researcherb

a Fidus Writer Project · b Institute for Document Engineering

Abstract. We demonstrate that print-quality PDF documents can be produced entirely inside a web browser, without invoking the browser's print dialog. A pagination engine lays out HTML and CSS Paged Media in a hidden frame; a lightweight emitter then re-renders the measured layout as a vector PDF. We evaluate the approach on a document containing running headers, footnotes, tables that span page breaks, and both vector and raster figures. The resulting PDF additionally carries clickable link annotations, document metadata, a bookmark outline, viewer preferences, and its own HTML source as an embedded attachment — structures the print dialog cannot produce.

Introduction

Producing PDF documents from structured markup has traditionally required server-side tooling or a detour through the browser's print dialog.Print-dialog workflows cannot be automated and produce PDFs whose fonts and margins vary between browsers. Both options are awkward for applications that already hold a complete, styled document in the DOM. This prototype explores a third path: paginate with CSS Paged Media in the browser and emit the resulting layout directly as PDF bytes.

The approach rests on two observations. First, a modern pagination engine can resolve @page rules, running headers, footnotes and page counters entirely in JavaScript. Second, once pagination has run, every glyph's position is knowable through standard geometry APIs such as Range.getClientRects(). Re-rendering those positions with a PDF writer yields a faithful, fully vector document."Faithful" here means glyph-identical for text and pixel-identical for raster content; vector figures are rasterized in the current prototype.

The Pagination Pipeline

Overview

The pipeline consists of four stages, executed in order; Figure 1 illustrates them.

  1. Assembly. The source document — HTML with embedded CSS Paged Media rules — is handed to the vivliostyle pagination engine together with a base URL so that fonts and images resolve.
  2. Pagination. The engine lays the document out in a hidden frame, producing one container element per page, including margin boxes for headers and footers:
    • page area with flowed content,
    • footnote area at the bottom of the page,
    • generated margin content (page numbers, running titles).
  3. Measurement. For every page, text is measured word by word; images, backgrounds and borders are measured by element.
  4. Emission. The measured items are drawn into a PDF using pdf-lib (the maintained @pdfme/pdf-lib fork) with flipped Y coordinates and embedded subsetted fonts; link annotations, document metadata, a bookmark outline and the source HTML attachment are added, and the file is downloaded.

Inline styles

Emitter sketch

The core loop of the emitter is deliberately simple: 

for (const page of pages) {
  const pdfPage = doc.addPage(sizeOf(page))
  paintBackgrounds(page, pdfPage)
  paintBorders(page, pdfPage)
  await paintImages(page, pdfPage)
  for (const word of collectWords(page)) {
    pdfPage.drawText(word.text, {
      x: word.x * PX_TO_PT,
      y: pageHeight - word.baseline * PX_TO_PT,
      font: pickFont(word.style)
    })
  }
}

Because each word is positioned from its own measured rectangle, browser line breaking, justification and hyphenation are preserved exactly; the emitter never re-breaks a line.Justified text survives because inter-word positions are copied, not the spacing rules that produced them.

Figures

The pipeline must handle vector and raster figures alike. Figure 1 summarizes the pipeline introduced in Section 2; Figure 2 is a PNG generated by a build script; Figure 3 is another SVG. SVGs are rasterized at 2x resolution during emission; keeping them vector via the fork's drawSvg() was attempted, but it drops arrow markers and mis-sizes text labels, so raster stays for now.

Discussion

As the feature matrix in Table 2 shows, several approximations remain, and Figure 3 hints at the cost of one of them. Text baselines are derived from font metrics rather than the browser's internal line boxes, which can shift glyphs by a fraction of a point. Underlines are not painted, so links appear as colored-only text even though their annotations are clickable. Backgrounds and borders are painted in document order, a simplification of the CSS stacking model that suffices for the table styles used in this report but would break on overlapping content. List markers are synthesized approximations, small caps are drawn as scaled uppercase glyphs rather than real smcp substitutions, and hyphens inserted by browser hyphenation would not be reproduced. Tagged PDF and PDF/A output remain out of scope.

None of these limitations is fundamental. Baselines can be taken from getClientRects() of per-character ranges during a calibration pass; real small caps would come from OpenType shaping in the emitter; paint order can follow the CSS specification more closely as needed.The fork's drawSvg() was evaluated for vector figure emission; it drops <marker> arrowheads and sizes <text> with fallback font metrics, so figures stay rasterized at 2x for now.

Conclusion

A browser-only pipeline — paginate with CSS Paged Media, then re-render the measured layout as PDF — produces automatable, deterministic, fully vector documents without server round-trips or print dialogs. The prototype documented here handles headers, footers, footnotes, cross-page tables, and figures, and its output goes beyond what the print dialog can offer: clickable external and internal link annotations, document metadata, a nested bookmark outline that viewers open automatically, viewer preferences, and the document's own HTML source embedded as an attachment. It is a viable foundation for production export in document-centric web applications.
